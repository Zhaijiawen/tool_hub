## pandoc 线上 "expected magic word ... found 3c 21 64 6f" 根治

- **第 3 次复现**同一报错。根因定位：
  - `public/wasm/pandoc.wasm.gz` 此前被 `.gitignore` 排除、完全未被 git 追踪，线上 dist 里的
    pandoc 资产**完全依赖 Cloudflare 构建期 `ensure-assets` 生成**；该步骤在 CI 未稳定产出时，
    缺失文件被 SPA 回退成 `index.html`，fetch 拿到 `<!doctype`（3c 21 64 6f）喂给
    `WebAssembly.instantiate` 报错。
  - 对比 `ffmpeg-core.wasm.gz` 在 `git ls-files` 中**已追踪** → 线上稳定，印证「入库即确定进 dist」。
- **修复（commit 71c67af）**：
  1. `.gitignore` 移除 `public/wasm/pandoc.wasm.gz` 忽略项（原始 56MB `pandoc.wasm` 仍忽略），
     改与 ffmpeg 一致：压缩产物入库，确定性保证 dist 包含。
  2. `useWasmModule.js` 加固：fetch 后先判 SPA 回退（`<!` → 视为资源缺失，抛清晰错误）；
     解压后再校验 wasm magic；**只对有效资源写 Cache API**；命中缓存中的脏 HTML/非法字节时
     自动 `evictCache` 自愈，避免一次失败后永久被脏缓存锁定。
- 验证：本地 `pandoc.wasm.gz` 15.5MB（< Cloudflare 25MB）、gzip magic 1f 8b、解压 55.9MB、
  wasm magic 00 61 73 6d 均正确。
- **待用户操作**：push 到远端并重新部署（Cloudflare 通常 push 即触发）；已改代码已 commit 未 push。
- 教训：被 gitignore 的大体积 wasm 资产若要线上稳定，应入库压缩产物（ffmpeg 即此模式），
  不要单靠 CI 构建期生成。后续 imgly/whisper/mermaid 若再出同类问题，同理处理。

## SQLite：首次进入 OPFS 置灰、创建临时库后才恢复的修复

- **症状**：SQLite 工具首次进入时 OPFS 单选框是灰色（disabled），但「新建临时库」（内存库）
  后 OPFS 选项就可用了。
- **根因（代码证据）**：
  - vendored `sqlite-wasm/index.mjs` 把 `installOpfsVfs()` 注册为**一次性**异步初始化器
    （`initializersAsync.push`，15808 之前的 `installOpfsVfs().catch(...)` 把失败静默吞掉）。
  - OPFS VFS 安装依赖 spawn 一个 async proxy worker（`sqlite3-opfs-async-proxy.js`），
    bindVfs 里有 4s `zombieTimer` 超时；**首次冷启动若该 proxy worker 偶发加载慢/超时**，
    `installOpfsVfs` reject 被吞 → `sqlite3.oo1.OpfsDb` 永不挂载 → `opfsUsable()` 永久 false。
  - 主线程 `opfsAvailable` 只在 worker `toolhub:sqlite-ready` 回执时设置一次，之后不更新
    （useSqlite.js:56）。所以一旦首次检测误判 false，UI 永久置灰。
  - 「创建临时库后好」的机制：该操作（或随之的路由/组件重挂载）触发 `useSqlite` 重新
    初始化、新 worker 重跑 init，第二次 `installOpfsVfs` 成功 → 点亮。属偶发恢复。
- **修复**：
  1. vendored `index.mjs`：在 `installOpfsVfs` 定义后、作用域内加回官方本就有的
     `sqlite3.installOpfsVfs = installOpfsVfs`（此前被打补丁时删掉），使其可外部重跑。
  2. `sqlite-worker.js` init：若 `!opfsUsable() && self.crossOriginIsolated`，延迟 1.5s 重试
     `installOpfsVfs()`，成功发 `toolhub:sqlite-opfs-ready` 主动点亮；新增 `probeOpfs` 消息
     供手动重试。
  3. `useSqlite.js`：监听 `opfs-ready` 更新 `opfsAvailable`，新增 `retryOpfs()` 向 worker 发
     `probeOpfs`。
  4. `SqliteTool.vue`：OPFS 不可用提示下加「重试检测 OPFS」按钮（调 `retryOpfs`）；
     en/zh i18n 补 `retryOpfs` 文案。
- 验证：`node --check` worker/composable 通过；`@vue/compiler-sfc` 编译 SqliteTool.vue 通过；
  vendored 暴露行位于 15808（installOpfsVfs 定义 15764 之后、sqlite3 作用域内）。
- 注意：未做浏览器实测（环境受限）。建议 push 后在支持 OPFS 的环境验证：首次进入若偶发置灰，
  应在 1.5s 内自动点亮，或点「重试检测 OPFS」手动点亮。

## ⚠️ 更正：SQLite「首次进入 OPFS 置灰」的真正根因

- 上一段（13d46ed）的诊断**打偏了**。该修复（installOpfsVfs 一次性初始化器被吞 + 重试点亮）
  只是稳健性补丁，**不是**首次置灰的主因。
- **真实根因（已部署验证：用户 push 后「问题还在」，证明 13d46ed 未命中主因）**：
  `ensureReady()`（下载 wasm + 启动 worker + 检测 OPFS）此前**仅在用户首次执行导入/打开动作时**
  才被调用，属于**惰性初始化**。首次进入页面 worker 根本未启动 → `opfsAvailable=false` →
  OPFS 单选框 `:disabled="!opfsAvailable"` 置灰。用户点「新建内存库」才触发 `ensureReady`、
  检测 OPFS 可用、回到打开面板后点亮——即「创建临时库后就好了」。
- **正确修复（commit d8c2108）**：`SqliteTool.vue` 在 `onMounted`/`onActivated` 即调
  `sqlite.ensureReady()` 预热，OPFS 状态在用户操作前就绪；`useSqlite.ensureReady` 加
  `initPromise` 并发守卫防重复起 worker；按钮在初始化期间禁用并显示进度。
- 教训：**「某动作后才正常」往往指向惰性初始化/首次副作用缺失，而非该动作改变了目标状态本身。
  先确认「状态在进页面时是否已被计算」，再去看 race。** 13d46ed 的 OPFS 自愈重试仍保留作安全网。
