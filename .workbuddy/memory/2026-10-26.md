## archive 解压卡「处理中」（libarchive comlink 握手竞态）

- 修复：
  1. `src/workers/libarchive-worker.js`：bundle import resolve 后 `self.postMessage({type:'toolhub:archive-ready'})`；catch 时发 `toolhub:archive-error`。
  2. `src/vendor/libarchive/libarchive.js` 的 `getClient()`：发 CONSTRUCT 前先 `await` worker 的 `toolhub:archive-ready`（带 30s 超时 + 监听 archive-error 拒绝），保证 comlink 已 expose 再握手。

## archive 创建压缩包报错（clone → undefined.size 两连击）
- 现象：点「创建压缩包」先报 `postMessage on MessagePort: [object Object] could not be cloned`，修掉后又报 `Cannot read properties of undefined (reading 'size')`。
- 两层根因（都在 `ArchiveTool.vue` 的 `createArchive()` 传参）：
  1. clone 层：`createFiles` 是 `ref([])`，`createFiles.value` 是 Vue reactive 代理**数组**，无法被 comlink `postMessage` 结构化克隆（与 OCR `selectedLangs.value` 同源 bug）。
  2. shape 层（克隆修掉后才暴露）：worker 的 `E.write` 期望 `files` 为 `Array<{file, pathname}>`，会 `e.reduce((a,{file:r})=>a+r.size+128)` 读 `element.file.size`。旧代码传裸 `File[]`，使 `element.file` 为 `undefined` → `undefined.size`。客户端的 `Archive.write({files,outputFileName,compression,format})` 内部 `a.writeArchive(files, compression, format, passphrase)`，故 files 必须是 `[{file}]`。
- 修复：`const plainFiles = createFiles.value.map((f) => ({ file: f }))` —— map 经 Vue rawIterator 返回普通数组（绕开代理），同时把裸 File 包成 `{file}`，pathname 省略时 worker 回退用 `file.name` 作条目名。
- 验证：纯 JS 取值/包壳，逻辑等价；未实机跑浏览器。尚未提交。

## archive 创建压缩包 0 字节 + `written bytes don't match file size`
- 现象：修掉 shape 后，选文件点创建，压缩包 0 字节，console 报 `Error occured while writing file, written bytes don't match file size`（来自 libarchive.wasm 内 C 绑定，非 JS 抛错，故 UI 拿到 0 字节结果而非 catch 报错）。
- 根因：`libarchive.js` 是 npm 包（^2.0.2），C 绑定预编译进 `libarchive.wasm`（仓库无 C 源码，不可改）。worker 的 `E.write` 用固定内存汇 `archive_write_open_memory(a, o, &used)`，缓冲区大小 `o = Σ(file.size + 128) + 128` 由 JS 估算。该估算**假设压缩后 ≤ 原大小 + 128**，对不可压缩/已压缩数据（zip/png/jpg/pdf/随机数据等）压缩输出会**超过** `file.size + 128`，内存汇溢出 → `archive_write_data` 写的字节数少于条目 size → C 打该错误、归档写废 → 0 字节。可压缩的单文件用旧估算本可通过，故用户测的是不可压缩数据。
- 修复：`src/vendor/libarchive/worker-bundle.js` 的 `write` 把估算改为 `o = Σ(ceil(file.size*1.1) + 4096) + 16384`，给压缩膨胀与归档头（本地头/中央目录/EOCD）留足余量。各压缩算法（deflate/gzip/bzip2/xz/zstd/lz4/store）不可压缩膨胀均 <0.1%，1.1x 余量充足。注意该 worker-bundle 是仓库 vendored 副本（`src/vendor/...`），非 node_modules 的 dist，改对位置。
- 验证：改后 `node --check` OK；未实机跑浏览器（用户本地验证）。尚未提交。
