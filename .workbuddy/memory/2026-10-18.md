### P1-1 已完成并提交：Mermaid 图表渲染（commit fb57236）

**重大工程教训（务必记住）**：mermaid **绝对不能交给 Rollup 打包**。
- 实证：引入后模块数 6735 → 8460，`vite build` 触发 V8 heap OOM；
  `NODE_OPTIONS=--max-old-space-size=6144`（6GB）仍被系统 SIGTERM 杀掉。
- 最终方案：沿用 imgly 的「大资产自托管 + 运行时懒加载」模式。取 `node_modules/mermaid/dist/mermaid.min.js`
  （5.2MB 原始 / 1.18MB brotli）复制到 `public/mermaid/`，组件运行时动态注入 script，
  加载后挂在 `window.mermaid`（该 esbuild IIFE 包尾部有 `globalThis["mermaid"] = ...default`）。
- 结果：默认堆构建 33s 通过，Diagram 路由块仅 9.02KB，`public/mermaid/` 入 .gitignore，
  由 `scripts/fetch-mermaid-assets.mjs` 获取。

**验证手法（可复用）**：不开 Chromium 也能验证 DOM 库——用 jsdom 加载自托管 bundle 跑 `parse()`，
再用本机 Chrome headless（`--headless=new --virtual-time-budget --dump-dom`）做真实渲染冒烟。
jsdom 需补 `structuredClone` / `SVGElement.prototype.getBBox` 否则会误报为语法错误。
本次结果：12/12 模板 parse 通过；Chrome 真实渲染 6/6 返回有效 SVG。

### P1-2 已完成并提交：图片转 SVG（trace，commit c1fe6d4）

选型从 `potrace-wasm@1.0.4`（299KB，GPL-2.0）落地，关键实测结论：
1. **导出守卫**：包用 `if (typeof module !== "undefined") { module.exports = {loadFromCanvas} }`，
   看起来是 Node 专用；但实测 Vite 的 commonjs 插件会把守卫**转为无条件块**，
   打包后 `loadFromCanvas` 正常可用（已用打包产物在浏览器验证）。
2. **前景语义**：Potrace 以**深色像素为前景**。黑底白图必须开启「反色」，否则输出实心黑块。
3. **fill-rule 无需修改**：输出的多条闭合子路径在 SVG 默认 `nonzero` 下挖空已正确
   （实测黑底白圆 → 中心白、角落黑），我原先的怀疑不成立。
4. wasm 内联为 base64 data URI，无外部请求；200KB 独立懒加载块（br 68KB），
   **不进首屏 bundle、不进 modulepreload**（注意：该块文件名叫 `index-*.js`，别误判成入口）。
5. 构建时 `fs` / `path` 被 externalize 的警告是无害的（仅 Emscripten 的 Node 分支）。

**MuPDF write options 硬约束（实测，已写进 worker 注释）**
1. **分隔符必须是纯逗号，带空格直接失败**：
   `'compress=yes,garbage'` OK；`'compress=yes, garbage'` 抛 `Unused pdf arguments found`。
2. **只识别特定键**：`garbage` / `compress=yes` / `compress-images` / `compress-fonts` /
   `decompress` / `linearize` / `pretty` / `clean`。
   臆测的 `garbage=compact`、`compress-images=yes`、`compression=jpeg`、`compression-effort=9`
   全部被判 unknown 并最终报 Unused pdf arguments。（早期笔记里的 `garbage=compact` 是错的。）
3. 可用组合实测通过的：`garbage,compress=yes,compress-images,compress-fonts`。

**压缩效果的真实数据（文案必须据此写，不可夸大）**

| 样本 | 结果 |
|---|---|
| 含未压缩图像的 PDF（扫描件，961KB） | → 465KB，**-51.6%** |
| Chrome「打印成 PDF」产物 | -1.4% |
| `clean` 或单独 `garbage` | 几乎无变化，甚至略增 |

结论：**只有未压缩过的 PDF 才有明显收益**，已优化文件收益极小。
UI 因此直接展示真实百分比，没变小则显示琥珀色「未能进一步压缩」，不假报成功。

**deletePage 索引平移（易错点）**
`deletePage(i)` 会移动后续页索引，删多页必须**倒序**执行，否则错位。
「保留模式」由 worker 换算为补集后再删。
边界：删全部 → `DELETE_ALL` 拦截；删不连续页 `1,3` → 实测剩余 1 页正确。

**提取文字是读文本层，不是 OCR**
`toStructuredText().asText()` 对扫描件返回空串，UI 必须显式提示改用 OCR 工具，
否则用户会误判成 bug。

**验证手法（可复用，很有价值）**

（`addEventListener` + `postMessage`），然后直接 `import()` 真实的
`src/workers/mupdf-worker.js`，喂真实 msg 端到端跑 job。

另用脚本比对「组件引用的 i18n 键」与「locale 定义的键」，69 键中英双向无缺失。

注意：截取 Vue SFC 模板时不能用 `src.index('</template>')`——会命中
`<template #header-extra>` 的闭合标签，导致只截到前几行、校验变假通过。

## Whisper 浏览器实机验证（已闭环）

用 agent-browser（Chrome 155，COOP/COEP 已在测试服务器 `/tmp/spa-server.mjs` 对齐生产 `_headers`，`crossOriginIsolated: true`）跑真实端到端。**关键教训：路由是 `/media/speech-to-text`，不是 `/tools/...`**——用错路径时 SEO title 仍正确但路由视图为空，易误判为渲染故障。

**修掉的 3 个问题**：
1. **ort 版本错配（浏览器端推理崩溃）**：手动 vendored `onnxruntime-web 1.19.2`，而 `@xenova/transformers 2.17.2` 硬锁 1.14.0。ort 1.17+ 把 `Tensor.data` 改为原型 getter（自有数据在 `cpuData`），transformers 用 `Object.assign(super, new ONNXTensor(...))` 浅拷贝拷不到 → 报 `Cannot use 'in' operator to search for 'subarray' in undefined`。**解法：顶层留 1.19.2 供 `@imgly/background-removal` 的 `onnxruntime-web/webgpu` 子路径解析，嵌套装 1.14.0 于 `@xenova/transformers/node_modules/`，vite alias 指向嵌套的 `ort.wasm.min.js`；fetch 脚本改取两个 `.wasm` 变体（1.14 无独立 `.mjs`，线程胶水内联在包 JS 内由内部 Blob 创建）。** Node harness 之前能过是因为它走 `onnxruntime-node` 兼容实现，掩盖了这个错配。
2. **n-upload `:max="1"` 静默吞掉重选**（`SpeechToText.vue`）：`clearFile()` 只重置本地 `file` ref，不清 n-upload 内部 `uncontrolledFileListRef`；下次选择时 `Upload.mjs:431` 的 `fileAndEntries.slice(0, max - mergedFileListRef.value.length)` = `slice(0, 0)` → 新文件被丢弃且不报错。**修法：给 `<n-upload>` 加 `ref`，在 `clearFile()` 里调 `uploadRef.value?.clear()`**（时序安全：`doChange` 先触发 onChange 再 `doUpdateFileList`，正常上传后列表仍写回新文件）。
3. **空结果无解释**：识别成功但文本为空时只显示「字符数: 0」，用户无从判断。新增 `emptyResult` 状态 + 中英 warning 文案（`media.speechToText.emptyResult`）。

**一处被推翻的假设**：`return_timestamps: true`（布尔）曾被怀疑是 transformers.js 不支持导致空结果。Node 对照实验证伪——ja/jfk 在 `true` 下都正常（chunks=1，时间戳 `[0,11]`），文档里的 `'word'` 是**词级**对齐而非修 boolean。真正的空结果来自 **fr.wav 音频本身电平过低**（peak 0.0626 / rms 0.0058 / 静音 42.8%，比正常低约 21dB）；且浏览器 Web Audio 解码比 Node 手写 WAV 解码器保真，fr.wav 在浏览器里能出 139 字符、在 Node 里为空——**跨环境解码差异大，音频测试样本不能只靠 Node harness 判定**。

**验证矩阵（全部通过）**：首页 90 工具/11 分类；媒体区双徽标（新 + WASM）；SEO 标题；jfk.wav 转写 107 字符；ja.wav 转写保留日文 / `task:'translate'` 出英文（"I hope you like this video."）；时间戳分段 `[00:00 → 00:11]` + SRT 按钮条件渲染；清空→重传回归 3 次；静音文件触发空结果警告；jfk 回归无警告。

### 二次复查：流式中间结果完全失效（3 处叠加，已修）

用户追问「还有其他问题吗」，逐层排查发现「实时显示中间结果」这条**默认勾选的功能从未真正工作过**，由三个问题叠加而成：

1. **`SpeechToText.vue` 的 `run()` 没传 `onChunk`**：`useWhisper.transcribe` 里 `onChunk: opts.onChunk ? ... : null`——不传则 `partialText` 永不累积，且 worker 发来的 chunk 消息在 `handleMessage` 中因 `job.onChunk` 为 null 被**静默丢弃**。实机确认 `running: true` 期间 `.partial` 区域一次都没出现过。
2. **`whisper-worker.js` 读的 `chunk.text` 恒为空**：transformers.js 的 `chunk_callback(chunk)` 收到的 chunk **尚未解码**——只有 `tokens`（token id 数组）、`stride`、`input_features`；`text` 要等后续 `_decode_asr()` 合并时才生成。直连 worker 实测：70s 音频触发 4 次 chunk 回调，每次 text 都是 `""`。**修法：worker 内用 `transcriber.tokenizer.decode(chunk.tokens, { skip_special_tokens: true })` 就地解码**（逐窗口 try/catch，单窗失败不中断整体）。
3. 二者互相掩盖：先修 1 会看到「有回调但文本空白」，只有两层都修才真正出文本。**排查这类「功能不生效」的问题，不能只改一层就下结论。**

**验证方法**：必须用 **>30s 的音频**才能触发分块（whisper 单窗 30s，短音频一次性算完，chunk 回调窗口太短采样不到）。jfk.wav 只有 11s，反复采样都抓不到。改用「jfk.wav 解码后重复 4 次 = 44s」直连 worker 验证：3 个 chunk 分别带真实文本（" And so my fellow Americans ask not what your coun" / " You can do for your country..." / " for you as what you can do for your country."），最终 387 字符。另外用 Python 合成的 70s 正弦波音频**测不出效果**——它本就无语音内容，结果恒为空会误导判断（此前我一度以为解码逻辑仍有问题）。**测流式必须用真实语音。**

**另外两处修复**：
- `handleFileChange` 的音频时长探测竞态：快速换文件时旧 probe（最长等 3s）可能晚于新文件返回，把上一段音频的时长显示到新文件上。加 `audioUrl` 身份校验 + `probe.src = ''` 释放解码器引用。
- 翻译任务下语言选择器标签歧义：Whisper 翻译目标恒为英文，标签改为「源语言」/「Source language」（新增 `sourceLanguage` 键，中英各 66 键一致）。

**教训沉淀**：验证「流式/渐进输出」类功能时，测试素材必须满足触发条件（本例是 >30s 真实语音），且要区分「回调没来」「回调来了但内容空」「内容正确」三种状态——它们指向完全不同的根因。

### 三次复查：n-upload :max 静默丢弃是**跨组件模式性 bug**（修 5 处）

前两次都是单点深挖，这次改策略做**模式性排查**：`grep ':max="'` 找到全部 n-upload 用法，逐一核对是否清理了内部列表。结果发现 SpeechToText 的 bug 在**另外 5 个组件同样存在**。

**判定标准**（比「有没有 clear()」更准确）：看 n-upload 是**受控**（`v-model:file-list`）还是**非受控**。
- 受控 → 组件把列表交给父组件管，重置 `fileList.value = []` 即安全
- 非受控 + 有 `:max` → 内部 `uncontrolledFileListRef` 持续占用 max 名额，**第二次选择被 `slice(0, max-len)` 静默丢弃且无任何报错**

| 组件 | max | 受控 | 症状 | 实机 |
|---|---|---|---|---|
| SpeechToText | 1 | ❌ | 点「清空」后无法重传 | ✅ 已修(b29e5e8) |
| **Rotate** | 1 | ❌ | **换图点了没反应** | 1770→1770 → 修后 1770→682 |
| **Watermark** | 1 | ❌ | 同上 | 1770→1770 → 修后 1770→682 |
