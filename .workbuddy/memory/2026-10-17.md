## UPGRADE-2 文件哈希改流式（GB 级）✅ —— 用户的性能判断已核实采纳

- 用户提问「只有 hash 值得做对吧，其他工具没性能问题吧，准备支持 GB 级文件」→ **核查发现其判断正确，但旧实现的严重程度超出预期**。
- **旧实现是假分块**：`FileHash.vue` 定义了 `CHUNK_SIZE = 2MB` 但**从未使用**，实际走 `readAsArrayBuffer` 整文件读入；且 `crypto.subtle.digest` **并发调三次**（SHA-1/256/512 各复制一份）→ 1GB 文件约 **4GB 峰值内存**。文案里"大文件分片处理"属**文案与实现不符**，一并修正。
- **技术前提**：Web Crypto 的 `crypto.subtle.digest()` **不支持流式**，只能一次性吃完整数据 —— 这是必须换库的根本原因（**不是 hash-wasm 更快，而是只有它能流式**）。
- **方案**：hash-wasm@4.12.0（MIT，Dani Biro），四算法共 32KB。4MB 分块 `file.slice()`（惰性视图不复制）+ 逐块 `update()`，四算法单次遍历同算；块间 `setTimeout(0)` 让出主线程避免进度条被饿死。新增取消按钮。
- **vendor 踩坑（重要）**：① 上游只提供 **UMD** 且无 `exports` 字段 → 子路径 `hash-wasm/md5` 构建直接 "failed to resolve"；② **更隐蔽**：直接 import 时 **Rollup 把 UMD 当 CJS，`createSHA256` 在产物里但内嵌 base64 载荷被丢弃**，运行时 `WebAssembly.compile()` 拿空 BufferSource 失败 —— **构建期不报错、只在运行时暴露**。故 vendor + 打补丁（注入 `self.__toolhubHashWasm[algo]`，并剥离 base64：66KB→23KB）+ 从 glue 正则抽 wasm 到 `public/wasm/*.wasm`（3.5/5.6/9.7/13.5KB，magic 校验）。
- **hash-wasm API 坑**：导出是具名对象 `{createSHA256, sha256}` 非默认导出；`createXXX()` 返回 **Promise**；**没有 `hex()`**（`digest()` 直接返 hex）；工厂名 `createMD5` 全大写（`create${name[0].toUpperCase()}` 拼的 `createMd5` 不匹配）。
- **实证**：与 Node 原生 crypto 逐字节比对全部 MATCH（2MB 分块 / 1 字节×1000 / 空输入 / 非 2 幂分块 / 3MB+777 任意分块 × 四算法）；反向不注入时明确失败 `BufferSource argument is empty`，**不会静默产出错误哈希值**。性能 MD5 455 / SHA-1 714 / SHA-256 312 / SHA-512 500 MB/s → **1GB 约 1–3 秒**；**100MB 流式哈希堆增量仅 0.6MB**。
- 构建：6739 modules（基线 6735 +4）；dist 五产物（FileHash 6.7KB + 四算法各 ~5.6KB 独立 chunk）；无 base64 泄漏。
- **教训**：卸载 spark-md5 前用了 `grep --include` 过滤，漏掉 `custom/ScriptBox.vue` 的动态 import 导致构建失败 —— **卸载依赖前必须全量 grep 不加路径过滤**。已恢复（ScriptBox 仍需）。
- **其余工具性能结论（可暂缓）**：文本/加密类走输入框无压力；图片/OCR/EXIF 整读但单文件通常 <20MB；**Archive/FileCompress 是第二优先**（已有流式基础 + 有 GB 级真实需求）；PDF/FFmpeg 受 MEMFS/WASM 堆上限约束非算法问题。

## UPGRADE-3 压缩/归档的 GB 级能力（A+C 方案）✅ + 用户确立取舍原则

- **用户新原则（重要，后续长期适用）**：「后续如果成本非常高的工具（比如底层改造），可以不做」+「WASM 是手段非目的，只有在性能/能力上有明显优势时才用」。
- **能力核查（三格式不对等，决定了方案）**：① **gzip 走原生 `CompressionStream`，是真流式 API**，可逐块喂；② brotli/zstd 的 wasm 绑定**只有 whole-buffer API**（`brotliCompress(bytes)` / `zstdCompress(buf)`），流式化需自己写分块 FFI（`BrotliEncoderCompressStream` / `ZSTD_compressStream2`）+ Worker 化，成本高 1–2 天且跨块状态依赖易错；③ **输出侧无论哪种格式都必须生成完整 Blob**（浏览器暂无流式落盘的通用能力），故「输出全量驻留」是下限，无法靠计算侧改造消除。
- **A（gzip 真流式）**：旧实现是 `writer.write(整个ArrayBuffer)` —— 名义用流、实为整读。改为 **4MB 分块 `file.slice()`（惰性视图不复制）+ 逐块 `writer.write()`**；**消费端与生产端必须并行**（`reader.read()` 循环与写入同时进行），否则大文件会死锁；中断时 `writer.abort()` + `consume.catch(()=>{})` 避免未处理 rejection。新增实时进度条 + **取消按钮**。
- **C（分级体积防护）**：brotli/zstd 设 2GB 硬上限（超过直接禁用并提示改用 gzip）+ 500MB 内存警告；ArchiveTool 设 2GB 硬上限 + 1GB 警告（压缩比高的包解压后可能膨胀数倍，故按包体积保守设定）。**gzip 不设上限**（流式，安全）。文案如实说明限制与替代方案，不虚假宣传。
- **顺带清理**：FileCompress 不再在 `loadFile` 里整读文件（改为保留 `File` 引用按需取）；魔数嗅探从整读改为只读**前 8 字节**。
- **Vue 约束（本次踩到）**：`<script setup>` 里的**普通 const 不会暴露给模板**（函数声明可以）。阈值常量必须包一层 `computed` 才能在模板里用。
- 构建：6739 modules（无新增依赖，基线持平）；dist FileCompress 19.3KB / ArchiveTool 19.8KB。zh/en 语法复验通过。
