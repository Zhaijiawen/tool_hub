## WebpAvifConvert 转换报错修复（vendored jsquash glue）

- 现象：WebpAvifConvert.vue 点「转换」后，webp_enc_simd / avif_enc 抛
  `Error: [toolhub] vendored glue: wasm must be provided as a compiled WebAssembly.Module`，webp 与 avif 都失败。
- 根因：jsquash 的 Emscripten glue（`webp_enc.js`/`webp_enc_simd.js`/`avif_enc.js`）把
  `new URL("*.wasm", import.meta.url).href` 回退改成 `else { wasmBinaryFile = (()=>{throw...})() }`
  —— 这个是**顶层 eager throw**。但调用方 `initEmscriptenModule`（emscriptenUtils.js）走的是
  `instantiateWasm` 注入「编译好的 WebAssembly.Module」，而非 `locateFile`。Emscripten 在
  `if(Module["instantiateWasm"]){...return}` 早返回，根本不会走到 getBinary/getBinarySync；但顶层
  `else` 在模块求值阶段就先抛了，导致合法路径被打断。
- 修法（三文件一致）：
  1. `else` 分支改为 `wasmBinaryFile=undefined`（保留 Vite 构建安全：无 `new URL(...)` 静态解析死资产）。
  2. 把清晰报错下移到 `getBinary`（webp）/ `getBinarySync`（avif）：`if(wasmBinaryFile===undefined)throw ...`，
     这些函数只在「未提供 instantiateWasm」的误用情形才会被 instantiateAsync 调到，合法路径永不触发。
- 验证：三文件 `node --check`（.mjs）均 OK；`instantiateWasm` 分支仍在。
- 注意：非 SIMD 的 `webp_enc.js` 同样有此 bug（组件在 `simd()` 为 false 时回退用非 SIMD glue），一并修了。
- 未提交（与之前的 Diagram.vue toBlob 修复、package-lock.json 异常改动一起待处理）。

## OCR 工具识别失败（Worker.postMessage 结构化克隆报错）

- 现象：OcrTool.vue 点识别后提示 `识别失败: Failed to execute 'postMessage' on 'Worker': [object Object] could not be cloned.`
- 根因：组件里的 `selectedLangs = ref(['eng'])`，其 `.value` 是 **Vue reactive Proxy 数组**，
  经由 `engine.recognize → initialize → { langs: selectedLangs.value }` 被直接塞进
  `worker.postMessage`。**Proxy 无法被 structured clone**，故报错。
  （已用 node 验证：reactive 风格 Proxy 走 structuredClone 抛 `[object Array] could not be cloned`，
  佐证 Proxy 不能克隆。）
- 修法（在序列化边界统一兜底，避免任何调用方把响应式数据漏进 Worker）：
  - `src/composables/useTesseract.js` 新增 `unproxy()`，用 `toRaw` 递归去除 Vue reactive Proxy；
    ArrayBuffer / TypedArray（图片、语言包字节）**原样返回、绝不拷贝**，普通对象/数组逐键去代理，
    Date/Map/类实例等其它类型原样返回。
  - `ensureReady` 的 init 握手消息、以及 `send()` 的 job payload 在 postMessage 前都过一遍 `unproxy()`。
- 验证：`node --check` 语法 OK；逻辑测试确认 proxy 数组被转成普通数组、TypedArray 引用保留、
  净化后 payload 可被 structuredClone。
- 注意：`fileBuffer.value`（ArrayBuffer，ref 赋值 ArrayBuffer 时 `reactive()` 因 getTargetType=INVALID
  不包装）本就是普通 ArrayBuffer，不是代理；本次真正漏代理的是 `selectedLangs.value`。
- 未提交（同上，待统一处理）。

## OCR 工具识别失败（TessBaseAPI undefined）— 缺 load 步骤

- 现象：修完 postMessage 克隆错误后（消息能进 worker 真正执行），报错变为
  `识别失败: TypeError: Cannot read properties of undefined (reading 'TessBaseAPI')`。
- 根因：worker 内 `TessModule`（tesseract core wasm 实例）**只在 `load` action 里被赋值**
  （`worker-script/index.js` / `worker_bundle.js` 的 `load` 处理器：
  `Core({wasmBinary}).then(t => TessModule = t)`）。但主线程
  `TesseractEngine.recognize()` 只发了 `loadLanguage → initialize → recognize`，**从未发 `load`**，
  于是 TessModule 始终是 undefined，`initialize` 里 `new TessModule.TessBaseAPI()` 直接抛错。
  顺带解释了为何错在 TessBaseAPI 而非更早的 FS：`loadLanguage` 的 `TessModule.FS.writeFile`
  被 `if (TessModule)` 包着，TessModule 为 undefined 时**静默跳过**写语言包，initialize 才炸。
- 这是被上一个「postMessage 克隆错误」掩盖的潜在 bug：克隆错误时消息根本到不了 worker，
  load 缺失的真相被挡在前面；克隆修好后立刻暴露。
- 修法：`src/composables/useTesseract.js` 新增 `TesseractEngine.loadCore()`，发 `load` action
  （payload `{ options: { lstmOnly:true, corePath:null, logging:false } }`），并在 `recognize()`
  **最开头** `await this.loadCore()` 后，再 `loadLanguages` / `initialize`。worker 端 `load` 对已存在的
  TessModule 幂等（`if (!TessModule)`），重复/二次识别无副作用。
- 验证：`node --check` 语法 OK；`dispatchHandlers` 与 `getCore` 已确认会正确路由/返回注入的 coreFactory。
- 进度显示小注（既有、非本次引入、未改）：组件在 `recognize()` 前已把 phase 置为 `recognizing`，
  故 `load`/`loadLanguage` 回报的 `loading tesseract core`/`initializing tesseract`/`loading language
  traineddata` 进度（受 `phase==='initializing'` 守卫）不更新进度条，识别阶段才跳变——属既有 cosmetic 行为。
- 未提交（同上，待统一处理）。

## PythonTool 白屏（n-space size="2px" 触发 naive-ui 崩溃）

- 现象：进 Python 工具页直接白屏，控制台 `[Vue warn] Unhandled error during execution of render function`
  + `naive-ui.js ... TypeError: Cannot read properties of undefined (reading 'split')`。
- 根因定位：错误在 `naive-ui.js` 第 1087 行 `seemly` 的 `getGap(value)`（`const [r,c]=value.split(" ")`），
  `value` 为 `undefined`。调用方是 `n-space` 的 `margin` computed：当 `size` 是字符串且**非预设键**
  （tiny/small/medium/large）时，它去主题 `self[createKey("gap", size)]` 查 `gap2px`，space 主题只定义了
  `gapSmall/gapMedium/gapLarge`，查不到 → `gap=undefined` → `getGap(undefined)` 抛错，整页 render 失败白屏。
  源码：`PythonTool.vue:11` 的 `<n-space vertical size="2px">`——`"2px"` 是非法 size 值。
- 修法：`PythonTool.vue:11` `size="2px"` → `:size="2"`（数字即像素，2px 行/列间距，符合原意图）。
- 排查：用 grep 扫全项目 `n-space` 的 `size` 用法，其余均为预设或数字/数组，仅此一处非法，已修。
- 未提交（同上，待统一处理）。

## SQLite OPFS 灰色（worker 误判 bug）

- 现象：SQLite 工具里 OPFS 持久化单选框灰色、只能选临时内存库。用户确认 `crossOriginIsolated===true`
  （COOP/COEP 头生效、安全上下文满足），故不是环境问题，而是判定 bug。
- 根因：`toolhub/src/workers/sqlite-worker.js` 用 `'opfs' in sqlite3` 判定 OPFS 可用性。但 vendored
  `sqlite-wasm/index.mjs` 在正常（非测试）上下文会经 `asyncPostInit -> postInit`（4740-4743 行）**删除
  `sqlite3.opfs` 工具对象**，于是 `'opfs' in sqlite3` 在正常环境**永远为 false**——与浏览器/COOP-COEP
  无关，纯属误判。真正的可用标志是 `installOpfsVfs()` 成功后挂在 `sqlite3.oo1.OpfsDb` 上的构造器。
- 时序：bootstrap 的 `asyncPostInit` 先跑 `initializersAsync`（含 `installOpfsVfs`）再 `postInit` 删
  `sqlite3.opfs`，整链完成才 resolve `sqlite3InitModule`，故 worker 拿到 sqlite3 时 `OpfsDb` 是否已挂载已确定。
- 修法：worker 新增 `opfsUsable()`（返回 `!!(sqlite3.oo1 && sqlite3.oo1.OpfsDb)`），替换 3 处
  `'opfs' in sqlite3`（ready 握手 `opfs` 字段 + import/openOpfs 的 `OPFS_UNAVAILABLE` 校验）。
- 验证：`node --check` 语法 OK；逻辑测试确认 OpfsDb 存在→true、缺失/null→false。
- 未提交（同上，待统一处理）。
- 长期坑已记入 MEMORY.md「vendored sqlite-wasm 的 OPFS 可用性判据陷阱」。
