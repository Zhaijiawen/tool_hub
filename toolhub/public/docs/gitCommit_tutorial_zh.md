# Git Commit 生成器 — 怎么用

这个工具帮你快速拼出符合 Conventional Commits 规范的提交信息，不用记格式。填表、复制、贴到 `git commit -m`，完事。

## 一步步来

**提交类型 —** 先选这次改动是什么性质。下拉菜单里有主要的类型：

- **feat** — 实现了之前没有的新东西
- **fix** — 修了个 bug
- **docs** — 只改了文档或注释
- **style** — 调了格式，逻辑完全没动
- **refactor** — 重构了代码，行为不变
- **perf** — 让什么东西变快了
- **test** — 加了或改了测试
- **chore** — 依赖、构建脚本、配置文件的改动

**Scope（可选）—** 括号里的简短标签，说明改的是哪块。常见写法：`feat(auth)`、`fix(payment)`、`refactor(user)`。团队内部统一 scope 命名方式，不用每个人起不同的名。全局改动就留空。

**Subject —** 一句话描述。用现在时、动宾结构（"新增"不要"新增了"）。控制在 72 个字符以内，超了工具会提示。说的是「改了什么」，不是「怎么改的」。

**Body（可选）—** 复杂改动加说明。为什么改？考虑过其他方案吗？写清楚帮 reviewer 也帮几个月后的自己。

**破坏性变更开关 —** 这次改动会导致现有功能坏掉就打开。描述什么坏了、怎么迁移。

**Issues —** 关联的 issue 编号，比如 `#123, #456`。输出的提交信息会自动带上 `Closes: #123, #456`。

## 复制和历史

预览区实时显示拼接好的提交信息。「复制完整 Commit」拿整条消息，「仅复制标题行」只拿第一行。每次复制都会存进历史记录（保留最近 5 条），点历史记录可以回填到表单，方便参考类似的历史提交。

## 几个好习惯

一次提交只做一件事——别把修 bug 和加新功能塞一起。破坏性变更一定要标，哪怕你觉得没人用那个接口。scope 全团队统一命名。提交前看一眼预览，确认信息准确表达了你的改动意图。
