# AES 技术背景

AES（高级加密标准）是目前使用最广泛的对称分组密码。你每次访问 HTTPS 网站、解锁密码管理器、或者连上 VPN，底层都有 AES 在默默工作。它由 NIST 在 2001 年标准化，之前的密码竞赛中胜出的算法叫 Rijndael，由比利时密码学家 Joan Daemen 和 Vincent Rijmen 设计。

## 竞赛是怎么赢的

这个背景挺有意思，能帮你理解 AES 为什么长这样。1997 年，NIST 发布公告：DES 已经不行了（56 位密钥？在 90 年代后期？），需要找一个能撑几十年的替代品。十五个团队提交了候选算法，1999 年筛选出五个决赛选手 -- MARS、RC6、Rijndael、Serpent 和 Twofish -- 2000 年 Rijndael 胜出。

评审标准不只是安全性。他们要的是在 8 位单片机和大型服务器上都跑得快的算法，要足够简单让人能正确实现，还要省内存、省功耗。Rijndael 全部满足，而且二十多年过去了，这个选择依然站得住脚。至今没有人找到实际可行的 AES 破解方法 -- 目前最好的攻击是针对 AES-256 的相关密钥攻击，能把复杂度从 2^256 降到大约 2^99.5，这理论上是个大新闻，但实际中毫无意义，因为攻击者需要掌握不同密钥之间的关系，而这种场景在真实系统中根本不会出现。

## 分组和密钥

AES 始终处理 128 位（16 字节）的分组，不多不少。但密钥可以是三种大小：

- **AES-128**：128 位密钥，10 轮变换
- **AES-192**：192 位密钥，12 轮
- **AES-256**：256 位密钥，14 轮

轮数越多安全性越高，但计算量也越大。大多数场景下 AES-128 就够用了 -- 目前没有已知攻击能实际威胁它，即便是假设中的量子计算机用 Grover 算法，也只是把有效安全性降到 64 位，仍然需要 2^64 次操作，目前没人能做到。AES-256 更适合需要长期保密的数据，或者合规要求更高的场景。

那 16 字节的分组在内部被排列成 4x4 的矩阵，叫作状态数组。每一轮经历四个操作：

```
SubBytes   -- 每个字节通过一个精心设计的 S 盒做非线性替换
ShiftRows  -- 每一行循环左移不同的位数
MixColumns -- 在有限域中用矩阵乘法混合各列
AddRoundKey -- 将状态与从原始密钥派生出的轮密钥做异或
```

第一轮直接做 AddRoundKey，最后一轮省掉 MixColumns（那里再做就多余了）。解密就是按相反顺序执行逆操作：InvShiftRows、InvSubBytes、AddRoundKey，然后 InvMixColumns。

## 设计的巧妙之处

S 盒值得特别说说。它是一个 256 项的查找表，但不是胡乱编的 -- 每一项都是 GF(2^8) 中的乘法逆元再经过仿射变换得到的。正是这种数学基础给了 AES 抵抗差分和线性密码分析的能力。ShiftRows 和 MixColumns 提供扩散：改变一个输入位，大约一半的输出位都会翻转（雪崩效应）。混淆加扩散，这是 Shannon 定义的密码设计经典配方，AES 执行得非常漂亮。

## 模式比算法本身更关键

刚接触密码学的时候没人告诉我这件事：密码算法本身很少是弱点，真正容易出问题的是你选的操作模式。纯 AES 一次只加密一个 16 字节的分组，要加密更长的数据，就得选个操作模式。

**ECB（电子密码本）**是你基本不该用的模式。每个分组独立用同一个密钥加密，相同的明文产生相同的密文。你可能见过那张著名的 Linux 企鹅图片，经过 ECB 加密后还能看出企鹅的轮廓 -- 这就是问题。ECB 会泄露数据模式，而模式泄露就是安全漏洞。

**CBC（密码分组链接）**通过把每个明文分组与前一个密文分组异或来解决这个问题。第一个分组需要随机的初始化向量（IV）。这是几十年的主力模式，但它不提供认证 -- 有人篡改密文你完全不知道。而且加密是严格串行的（没法并行），不过解密可以并行。

**CTR（计数器）**把 AES 变成流密码。你加密一个计数器值，然后把输出和明文异或。每个分组相互独立，加密解密都能并行处理。高吞吐场景的利器，但千万别用同一个密钥重复使用同一个计数器 -- 那是灾难性的失败。

**GCM（Galois/计数器模式）**是现代的默认选择。它在 CTR 模式的基础上加上基于伽罗瓦域乘法的认证标签，一次操作同时提供加密和完整性保护，硬件上还特别快（不过在某些没有无进位乘法指令的平台上，软件性能可能不太理想）。TLS 1.3 用 GCM，WireGuard 用 GCM，大多数现代协议都选了它。唯一要注意的：nonce 重复使用是致命的 -- 会暴露认证密钥，机密性和完整性一起完蛋。

## 性能和硬件

过去十年生产的 CPU 基本都有 AES-NI 指令集，用专用硬件跑 AES。这让 AES 从"挺快"变成了"几乎不花钱" -- 单核能做到每秒 GB 级别的吞吐量。软件回退方案到处都是（OpenSSL、Crypto++、Bouncy Castle、Go 标准库、Rust 的 aes crate），但速度要慢一到两个数量级。移动端和嵌入式中，ARM 也有自己的 AES 扩展。

有个容易被忽视的问题：侧信道攻击。软件实现的 AES 如果没有用恒定时间查找，就会通过缓存时序泄露密钥。S 盒查找是个典型例子 -- 如果查找地址依赖于秘密数据，攻击者测量缓存访问模式就能恢复密钥。现代库通过位切片实现或尽量用硬件 AES 来处理这个问题，但如果你在自研，这事必须上心。

## AES 的未来

AES 还会存在很久。即使在量子时代，Grover 算法也只是把密钥安全性减半 -- AES-256 面对量子攻击仍然有 128 位的安全强度，足够了。真正威胁 AES 部署的不是数学突破，而是实现缺陷、侧信道、模式误用和 IV 乱搞。选个靠谱的库，用 GCM 或 CBC+HMAC，从合格的 CSPRNG 生成 IV，基本就不会翻车。
