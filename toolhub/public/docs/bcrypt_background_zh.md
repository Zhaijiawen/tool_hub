# bcrypt 技术背景

bcrypt 是密码哈希的老前辈 -- 从 1999 年由 Niels Provos 和 David Mazières 设计至今，虽然 Argon2 是更新更强的选择，它依然是个靠谱的方案。它诞生于解决一个根本问题：如果你用 SHA-1 或 MD5 哈希密码，拿到数据库的攻击者用 GPU 可以每秒尝试数十亿个猜测。bcrypt 让它变慢。刻意地、优雅地变慢。

## 基于 Blowfish，但不是你以为的那种用法

bcrypt 用 Blowfish 分组密码作为核心原语，但并不用它做常规加密。它利用的是 Blowfish 出了名昂贵的密钥调度 -- 就是从密钥初始化密码内部状态（P 数组和 S 盒）的过程。普通 Blowfish 只做一次。bcrypt 的 "EksBlowfish" 变体做 2^cost 次，其中 cost 是你选择的工作因子。

然后算法用这个设置成本极高的密码去加密 24 字节的固定字符串 "OrpheanBeholderScryDoubt"（是的，这真的是常量 -- 1999 年的命名风格），输出就是你的密码哈希，和盐值、工作因子混在一起编码成标准的 60 字符字符串。

## 工作因子是核心

bcrypt 的核心洞察：成本参数是指数级的。工作因子 10 代表 2^10 = 1,024 次密钥调度迭代。工作因子 12 是 4,096 次。每加 1 时间翻倍。1999 年，工作因子 6 算合理。今天，12 是生产环境的实际底线，如果硬件允许，13 或 14 更好。

把工作因子嵌入哈希字符串本身（那种 `$2b$12$...` 格式）是天才设计，让你可以透明地升级。当硬件变快时，你的登录函数检查存储的工作因子，成功登录后用更高值重新哈希。用户无感知，攻击者难受。

有个容易踩的坑：bcrypt 最大密码长度是 72 字节。超过的部分被静默截断。如果你的用户用超过 72 字符的密码短语（其实不应该，但有些密码管理器会生成），你应该在传给 bcrypt 之前先用 SHA-256 或 SHA-512 预哈希。这就是 "bcrypt + SHA" 模式，广泛使用。

## 为什么能抵抗 GPU 和 ASIC

bcrypt 在 GPU 密码破解成为主要威胁之前就设计了，但它意外地表现出了很强的抗性。原因在于内存访问模式。bcrypt 的密钥调度需要反复读写 4 KB 的状态（Blowfish 的 S 盒和 P 数组），而且这些访问是数据相关的 -- 你无法提前预知接下来需要哪个字节。GPU 有数千个核心但每个核心的快速本地内存很小；GPU 破解 bcrypt 哈希会撞上内存带宽瓶颈，而不是计算瓶颈。

这本质上就是 Argon2 16 年后形式化的"内存密集型"设计理念。bcrypt 更早达到这个目标，不过内存占用更小（4 KB vs Argon2 的 64-512 MB）。更小的内存意味着 bcrypt 对 ASIC 攻击的抵抗力不如 Argon2，但远比 PBKDF2 或裸 SHA 哈希强得多。

## $2a$ 还是 $2b$

你有时会看到 bcrypt 哈希以 `$2a$` 开头，有时以 `$2b$` 开头。`2a` 变体在 1999 年的原始实现中有个 bug（和非 ASCII 字符处理以及密码长度检查中一个有符号/无符号的问题有关）。`2b` 变体由 OpenBSD 在 2014 年标准化，修复了这个问题。有些实现用过 `$2y$`（PHP 用过一阵子）和 `$2x$`（某些测试套件用的故意 bug 版）。新代码用 `$2b$`，任何现代库都应该默认使用它。

## bcrypt 还值得用吗

对新项目来说，Argon2id 是更好的选择 -- 抗 ASIC 攻击能力更强、原生支持长密码、可调节的参数更多。但 bcrypt 依然没问题。它经过了实战检验（25 年的真实世界攻击），每种语言都有审计过的实现，72 字节密码限制在实际中很少成为问题。如果你在维护一个已经用 bcrypt 的系统，没有紧急迁移的必要。如果你从零开始且有选择余地，Argon2id 略胜一筹，但用 bcrypt 也不算错。

真正的错误是用任何更弱的东西：MD5、SHA-1、无盐的 SHA-256，或者 -- 天理难容 -- 明文存储密码。bcrypt 是密码安全的地板，而不是天花板。
