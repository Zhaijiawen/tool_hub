# ChaCha20 技术背景

ChaCha20 是 Daniel J. Bernstein 在 2008 年发表的流密码，是他之前设计的 Salsa20 的改进版。用现代浏览器、WireGuard、或任何跑 TLS 1.3 的东西，你都在用 ChaCha20。Google 力推它进入 TLS 作为 AES-GCM 的替代方案，事实证明这个选择很棒 -- 软件实现快、设计简单、还能抵抗困扰一些 AES 软件实现的时序侧信道攻击。

## ChaCha20 为什么诞生

背后的故事其实很务实。AES 有硬件加速（AES-NI），在有这个指令集的现代 CPU 上 AES-GCM 极快。但如果 AES-NI 不可用 -- 比如老硬件、2015 年之前的大多数 ARM 设备、或者 AES-NI 指令没暴露出来的虚拟化环境 -- 软件的 AES-GCM 慢而且可能受缓存时序攻击的威胁。

Bernstein 设计 Salsa20（然后是 ChaCha20）的目标就是纯软件下就很快，不需要硬件支持。算法只用简单的操作：32 位加法、异或和位旋转。没有查找表、没有复杂的有限域数学。这天然就是恒定时间的 -- 执行路径不依赖数据，时序攻击也就无从下手。

ChaCha20 通过改进扩散特性来超越 Salsa20 -- 具体来说，改变了旋转常量，让输入差异更快地扩散到整个状态。每轮 ChaCha20 比 Salsa20 每轮扩散得更好，这意味着 ChaCha20 用更少轮数就能达到同样的安全裕度（所以叫 "20" -- 总共 20 轮，即 10 个双轮）。

## 大致的工作原理

ChaCha20 维护一个 512 位的内部状态，排列成 4x4 的 32 位字矩阵。状态初始化如下：

- 4 个字常量：字面值就是 ASCII 字符串 "expand 32-byte k"（这不是为了安全性 -- 只是一个域分隔符，区分 ChaCha20 密钥流和使用相同核心的其他用途）
- 8 个字密钥材料（256 位）
- 1 个字块计数器（32 位，从 0 或 1 开始）
- 3 个字 nonce（96 位）

每个输出"块"通过在这个状态上运行 20 个四分之一轮操作、然后把结果加回到原始状态（按字相加，不是异或）来生成。每个四分之一轮通过加法、异或和旋转来转换四个字：

```python
a += b; d ^= a; d = rotate_left(d, 16)
c += d; b ^= c; b = rotate_left(b, 12)
a += b; d ^= a; d = rotate_left(d, 8)
c += d; b ^= c; b = rotate_left(b, 7)
```

八个四分之一轮（每列两个、然后每条对角线两个）组成一个双轮，执行 10 个双轮就是总共 20 轮。每个块输出 64 字节密钥流 -- 因为计数器是 32 位的，一个密钥/nonce 对最多可以生成 256 GB 密钥流后才需要重新生成密钥。实际中你永远不会接近那个上限。

## 用 ChaCha20 加密：就是异或

作为流密码，ChaCha20 生成密钥流，用明文去异或得到密文。解密是完全相同的操作：密文和同样的密钥流异或得到明文。没有单独的加密和解密函数 -- 从头到尾都是对称的。

这和 AES 不同，AES 是分组密码需要选择操作模式。ChaCha20 天生就是流密码 -- 你可以一次加密一个字节。不需要填充，不需要对齐到块边界。对于消息长度变化很大的协议来说，这特别舒服。

## ChaCha20-Poly1305：真正管用的组合

实际上几乎没人用裸 ChaCha20。你用的是 ChaCha20-Poly1305，将 ChaCha20 加密和 Poly1305 认证配对。Poly1305 也是 Bernstein 的作品 -- 一个一次性认证器，用素数域上的多项式求值生成 16 字节标签。

ChaCha20-Poly1305 构造在 RFC 7539 中标准化，流程如下：
1. 用 ChaCha20 加密一个全零块得到 Poly1305 密钥
2. 用 ChaCha20 加密明文
3. 用上面派生的密钥把密文通过 Poly1305
4. 输出密文后跟 16 字节 Poly1305 标签

这给了你认证加密 -- 可以检测篡改，不用担心密文的位翻转攻击。TLS 1.3、WireGuard 和 Noise 协议框架都把 ChaCha20-Poly1305 作为主要密码套件之一。

## Nonce 管理：绝对不能搞砸的事

像所有流密码一样，ChaCha20 有一个绝对铁律：同一个密钥绝不重复使用 nonce。如果同一个密钥和 nonce 加密了两条不同的消息，攻击者可以把两个密文异或到一起得到两个明文的异或。这通常足以恢复两条消息。

好消息是：96 位 nonce 可以安全地用随机方式生成。碰撞概率极低（每对 2^-96）。换个说法，大概相当于一次猜对一个特定 UUID 的概率。大多数实现都用随机 nonce。

如果需要在同一个密钥下加密极大数量的消息（数十亿级别），应该用基于计数器的 nonce 方案而不是随机生成。

## 今天的位置

ChaCha20 取得了巨大成功。它是 TLS 1.3 的强制密码套件，是 WireGuard 的唯一密码，每个主流密码库都支持它。设计简单到有能力的程序员可以对着 RFC 用几百行代码写出正确的实现 -- 关于 AES-GCM 你绝对不敢说这话。

对大多数新应用来说，ChaCha20-Poly1305 和 AES-GCM 在安全性上基本可以互换。ChaCha20-Poly1305 在纯软件环境和移动设备上有优势。AES-GCM 在有硬件 AES 且需要极致吞吐量时胜出。选你用的库最方便的那个就好。
