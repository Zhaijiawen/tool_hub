# ChaCha20 Technical Background

ChaCha20 is Daniel J. Bernstein's follow-up to his own Salsa20 stream cipher, published in 2008. If you've used a modern web browser, WireGuard, or pretty much anything that does TLS 1.3, you've used ChaCha20. It's the stream cipher that Google pushed hard to get into TLS as an alternative to AES-GCM, and it's turned out to be a fantastic choice -- fast in software, simple to implement, and resistant to the timing side channels that plague some AES software implementations.

## Why ChaCha20 exists

The story is actually pretty practical. AES has hardware acceleration (AES-NI) on modern CPUs, and when that's available, AES-GCM is blazing fast. But when AES-NI isn't available -- think old hardware, most ARM devices before about 2015, or virtualized environments where the AES-NI instructions aren't exposed -- AES-GCM in software is slow and potentially vulnerable to cache-timing attacks.

Bernstein designed Salsa20 (and then ChaCha20) to be fast in pure software with no hardware support. The algorithm uses only simple operations that every CPU can do quickly: 32-bit addition, XOR, and bit rotation. No lookup tables, no complex finite-field math. This makes it naturally constant-time -- the execution path doesn't depend on the data, so timing attacks have nothing to measure.

ChaCha20 improved on Salsa20 by tweaking the diffusion -- specifically, changing the rotation constants to spread input differences through the state faster. Each round of ChaCha20 diffuses changes better than a round of Salsa20, which means ChaCha20 reaches the same security margin in fewer rounds (hence "20" -- 20 rounds total, or 10 double-rounds).

## How it works, roughly

ChaCha20 maintains a 512-bit internal state arranged as a 4x4 grid of 32-bit words. The state gets initialized with:

- 4 words of constants: literally the ASCII string "expand 32-byte k" (this isn't security -- it's just a domain separator to distinguish ChaCha20 keystream from other uses of the same core)
- 8 words of key material (256 bits)
- 1 word of block counter (32 bits, starts at 0 or 1)
- 3 words of nonce (96 bits)

Each "block" of output is generated by running 20 quarter-round operations on this state, then adding the result back to the original state (word-wise addition, not XOR). Each quarter round transforms four words through a sequence of addition, XOR, and rotation:

```python
a += b; d ^= a; d = rotate_left(d, 16)
c += d; b ^= c; b = rotate_left(b, 12)
a += b; d ^= a; d = rotate_left(d, 8)
c += d; b ^= c; b = rotate_left(b, 7)
```

Eight quarter rounds (two per column, then two per diagonal) make up one double-round, and you run 10 double-rounds for a total of 20 rounds. The output is 64 bytes of keystream per block -- since the counter is 32 bits, you can generate up to 256 GB of keystream from a single key/nonce pair before needing to rekey. In practice you'll never come close to that limit.

## Encryption with ChaCha20: it's just XOR

As a stream cipher, ChaCha20 generates a keystream that you XOR with plaintext to produce ciphertext. Decryption is the exact same operation: XOR the ciphertext with the same keystream and you get the plaintext back. There's no separate encryption and decryption function -- it's symmetric all the way down.

This is different from AES, which is a block cipher that needs a mode of operation. ChaCha20 is a stream cipher natively -- you can encrypt one byte at a time if you want. No padding needed, no block alignment. This makes it particularly pleasant for protocols where message lengths vary.

## ChaCha20-Poly1305: the pairing that matters

In practice, almost nobody uses raw ChaCha20. You use ChaCha20-Poly1305, which pairs ChaCha20 encryption with Poly1305 authentication. Poly1305 is another Bernstein creation -- a one-time authenticator that generates a 16-byte tag using polynomial evaluation in a prime field.

The ChaCha20-Poly1305 construction, standardized in RFC 7539, works like this:
1. Generate a Poly1305 key by encrypting a zero block with ChaCha20
2. Encrypt the plaintext with ChaCha20
3. Feed the ciphertext through Poly1305 using that derived key
4. Output the ciphertext followed by the 16-byte Poly1305 tag

This gives you authenticated encryption -- you can detect tampering and don't have to worry about bit-flipping attacks on the ciphertext. TLS 1.3, WireGuard, and the Noise protocol framework all use ChaCha20-Poly1305 as one of their primary cipher suites.

## Nonce management: the thing you can't screw up

Like all stream ciphers, ChaCha20 has one absolute rule: never reuse a nonce with the same key. If you encrypt two different messages with the same key and nonce, an attacker can XOR the two ciphertexts together and get the XOR of the two plaintexts. That's often enough to recover both messages.

The good news: with a 96-bit nonce, you can safely generate them randomly. The probability of collision is astronomically low (2^-96 per pair). For comparison, that's roughly the same probability as guessing a specific UUID correctly on the first try. Most implementations use random nonces.

If you need to encrypt a very large number of messages with the same key (billions), you should use a counter-based nonce scheme instead of random generation.

## Where it stands today

ChaCha20 has been a huge success. It's mandatory in TLS 1.3, it's what WireGuard uses as its only cipher, and it's available in every major crypto library. The design is simple enough that a competent programmer can implement it from the RFC in a few hundred lines of code and get it right -- something you absolutely cannot say about AES-GCM.

For most new applications, ChaCha20-Poly1305 and AES-GCM are essentially interchangeable from a security standpoint. ChaCha20-Poly1305 has the edge in software-only environments and on mobile devices. AES-GCM wins when hardware AES is available and you need raw throughput. Pick whichever your library makes easiest.
