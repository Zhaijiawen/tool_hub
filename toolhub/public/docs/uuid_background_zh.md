# UUID 与 NanoID — 唯一标识符是怎么回事

UUID 是一个 128 位的数字，设计目标是不需要中央协调就能全球唯一。你在自己笔记本上生成一个，可以确信世界上没人会生成一个一模一样的——哪怕别人也在同时生成数百万个。

## 主要的 UUID 版本

| 版本 | 原理 | 适用场景 |
|------|------|---------|
| v1 | 时间戳 + MAC 地址 | 有序但是会暴露 MAC 地址，别在公开系统里用 |
| v4 | 完全随机（122 位随机数）| 通用目的——用得最广泛的版本 |
| v7 | Unix 时间戳前缀 + 随机后缀（RFC 9562）| 有序且安全，数据库主键首选 |

标准格式：`xxxxxxxx-xxxx-Mxxx-Nxxx-xxxxxxxxxxxx`——32 个十六进制字符加 4 个连字符，共 36 字符。

## v7 有什么好

UUID v7 是更新的标准（RFC 9562）。前 48 位是毫秒级精度的 Unix 时间戳，让 v7 UUID 天然按创建时间排序。这对数据库来说是个大优势——随机的 v4 UUID 会导致索引碎片化，因为插入位置到处分散。v7 UUID 总是插在索引末尾，效果类似自增整数。

## NanoID：更短的替代方案

NanoID 是 UUID 的现代替代品，有几个优点：

- 默认 21 字符 vs UUID 的 36 字符——URL 和日志里省空间
- 使用 URL 安全字符（`A-Za-z0-9_-`）——不需要转义就能放进查询字符串
- 底层用 `crypto.getRandomValues()`——和 UUID v4 同级别的密码学安全
- 长度（4-128）和字符集可自定义——可以只要数字、只要小写字母

## 碰撞概率

UUID v4 有 122 个随机位，2^122 种可能。生成 10 亿个 UUID v4 后碰撞概率约 1/100 万亿——实际使用中可以当零看待。

NanoID 默认 21 字符、64 个字符的字母表，有 64^21 = 2^126 种可能——比 UUID v4 还略高。但把长度降到 10 就只有 64^10 = 2^60，虽然还是天文数字，如果要生成数十亿级别的 ID 就得留个心。
